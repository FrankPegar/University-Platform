# v1.4 — In-app notifications

Implemented October 5, 2026. Scope is fetch/poll-based in-app notifications only.

## Behavior

| Type | Action | Recipient |
| --- | --- | --- |
| `question_answer` | A student posts an answer | Question author |
| `question_comment` | A student comments on a question | Question author |
| `answer_comment` | A student comments on an answer | Answer author |
| `answer_accepted` | Question author accepts an answer | Answer author |

Self-actions are skipped. Repeated acceptance/re-acceptance of the same answer produces at most one acceptance notification. Edits, votes, unacceptance, and deletion do not generate new notifications. Deleting a related question, answer, or comment cascades deletion of its notifications to avoid dead links.

The header bell shows the unread count (`99+` visually above 99, with the full accessible count). It opens `/notifications`, which displays actor avatars/names, event text, current question title, created time, and read/unread styling. Pages contain 20 notifications. Clicking an item opens its question and marks it read; Mark all as read includes notifications beyond the current page.

The shared notification provider uses the existing auth context and API helper. It fetches on login/mount, bell opening, page changes, and window focus/visibility; while visible it polls every 30 seconds. State is reset by user/session, pending updates prevent duplicate requests, and older fetches cannot undo a completed read action. Loading, empty, fetch error/retry, and update error/retry states are included. Read-update errors remain visible after navigating to the question. Failed fetches preserve the last known count and list.

## Database and setup

Migration: `supabase/migrations/20261005033411_in_app_notifications.sql`.

**Already applied to the configured Supabase project and verified live.** No manual setup is needed for that project. The migration file version matches the recorded remote migration version. For another environment, apply the migration once before deploying the backend/frontend changes. No new environment variables or application dependencies are required.

The table stores UUID ID, recipient/actor profile references, type, related question/answer/comment references, `is_read`, and `created_at`. Foreign keys handle content/account deletion. Indexes cover recipient ordering, unread counting, and foreign-key lookups; unique source-event indexes prevent duplicate notification delivery.

RLS restricts SELECT, UPDATE, and DELETE to `recipient_id = (select auth.uid())`. Authenticated users have SELECT/DELETE and column-level UPDATE only on `is_read`; they cannot insert notifications or rewrite actors, recipients, or event targets. Anonymous users have no privileges. Only the backend service role creates events. Backend list/mutation queries independently scope every request to the verified user's ID and do not accept recipient IDs from the client.

## API

- `GET /api/notifications?page=1&limit=20` — `{ items, total, unread_count, page, limit }`; maximum limit 50. Unread count uses an indexed exact count across all recipient rows, not the returned page.
- `PATCH /api/notifications/:id/read` — mark an owned notification read; repeated requests are safe.
- `PATCH /api/notifications/read-all` — mark all of the current recipient's unread notifications read.
- `DELETE /api/notifications/:id` — delete an owned notification (API/security support; no additional deletion UI).

Foreign-recipient and missing IDs both return 404 for mutations, without disclosing another user's notification existence. Unsupported query/body fields are rejected.

Notification creation runs in the existing answer/comment services **after** successful content writes. It derives recipients from persisted question/answer ownership and actors from the verified request. Notification delivery errors are logged without reporting committed Q&A actions as failed.

## Remaining limitations

- Q&A writes and notification inserts are separate operations. A delivery failure or process interruption after content commit can lose that notification; failures are logged, but there is no durable retry queue/outbox in v1.4.
- Notifications can arrive up to 30 seconds later while the tab is visible; reopening/focusing refreshes sooner. No realtime, email, push, preferences, follows, or mentions were added.
- Acceptance notifications record a past event. Unaccepting does not retract one, and re-accepting does not generate another for the same answer.
- Pagination uses offsets; arrivals/deletions between page fetches can shift entries. No retention/automatic expiry policy was introduced.
- Mobile tests used emulation rather than a physical device.
