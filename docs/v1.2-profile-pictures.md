# v1.2 — Profile pictures

Implemented and verified September 23, 2026. Remaining browser/live verification was rerun successfully October 5, 2026, without changes to application code, tests, or migrations. Existing MVP and v1.1 editing behavior is preserved.

## Behavior

Edit Profile now includes picture selection, a local preview, Upload picture, Discard picture, and Remove picture. Picture actions save independently of the existing profile fields, as explained in the UI. They preserve unsaved name/department/course/year drafts. Cancel discards an unuploaded selection; it does not undo a completed picture upload.

- Inputs: JPG/JPEG, PNG, or WebP; maximum **2 MiB (2,097,152 bytes)** and **16 million pixels**.
- The backend decodes the image, verifies its format against the declared MIME type, removes metadata, and stores a static WebP thumbnail up to 512 × 512 pixels. Small images are not enlarged.
- A student has one predictable object: `avatars/<verified-user-id>/avatar.webp`. Cross-format replacements overwrite this same object.
- Removing a picture deletes the object and clears `profiles.avatar_path`.
- Profile, header user area, question cards/detail authors, answer authors and comment authors use the shared Avatar component. Missing or failed images fall back to initials.
- Upload/removal have pending states, duplicate-request protection and retryable errors. No percentage progress is fabricated.

## Supabase setup

Apply **`supabase/migrations/202609230001_profile_avatars.sql` before deploying the updated backend**. This migration has already been applied to the current project by the project owner and verified through live tests.

The migration:

1. Adds nullable `public.profiles.avatar_path`.
2. Adds a constraint allowing only `NULL` or that profile's own `<id>/avatar.webp` path.
3. Creates/configures the **private** `avatars` bucket with a 2 MiB file limit and `image/webp` storage MIME type. JPEG/PNG inputs are converted by Express before storage.
4. Allows authenticated image reads, and insert/update/delete only at the authenticated student's exact path.
5. Adds restrictive guards so unrelated permissive Storage policies cannot grant cross-student writes or anonymous access to this bucket.
6. Reloads the PostgREST schema cache.

No new frontend environment variables or Supabase SDK are needed. Existing server Supabase settings remain server-only. Install backend dependencies using `npm ci` in `server/`; Sharp requires **Node 20.9+**. Verification used Node 22.19.0.

Supabase Storage upsert requires read and update permissions in addition to insert; the migration includes these explicitly. [Supabase access-control documentation](https://supabase.com/docs/guides/storage/security/access-control).

## API and security

- `POST /api/profiles/:id/avatar`: raw image bytes with their image Content-Type and the existing bearer token.
- `DELETE /api/profiles/:id/avatar`: remove the current picture.
- Both routes verify authentication and require the URL profile ID to equal the verified user ID **before reading/processing an image**. Storage paths are derived exclusively from `req.user.id`, never from submitted filenames, user IDs or paths.
- Storage writes use a request-scoped Supabase client with the student's JWT, so Storage RLS applies to the application itself. The service-role client updates profile references and signs read URLs only on the backend.
- Existing profile PATCH validation still excludes `avatar_path`, `avatar_url`, `student_id`, and ownership fields.
- Profile/author responses add `avatar_path` and a generated `avatar_url`. The database stores only the path; URLs are signed for one hour and regenerated when profile/content data is fetched. Signing is batched per response, and signing failures leave other profile/Q&A data available with initials.
- A profile update timestamp in the image URL prevents the UI from reusing a stale replacement image. The live test verified the returned bytes through fresh signed URLs.

Private-bucket reads require authorization or a signed URL; signed URLs are temporary bearer links and are not service-role credentials. [Supabase bucket documentation](https://supabase.com/docs/guides/storage/buckets/fundamentals).

## Remaining limitations

- Storage and profile database updates are separate operations. A database failure after upload can leave one recoverable object; retrying overwrites it, and Remove cleans it up. A failure after deletion can leave a stale profile reference until removal is retried. No upload history or unlimited filename orphans are created.
- Existing signed URLs or downloaded images may remain in browser/CDN caches. Fresh profile/content responses provide versioned URLs; a removed image is immediately replaced by initials in the current UI. Expired/unavailable image links fall back to initials until refreshed.
- Pictures become static thumbnails; no animation or crop editor is added.
- Mobile checks used viewport emulation rather than physical devices. Existing MVP/v1.1 limitations remain as previously documented.

Stopped at profile pictures; no additional feature scope was introduced.
